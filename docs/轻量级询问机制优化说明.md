# 轻量级询问机制优化 - 使用说明

## 📋 优化概述

本次优化实施了**双重省流锁机制**，大幅降低了多客户端场景下的服务器负载和网络流量。

### 🎯 优化目标

- **场景**: 3台电脑同时运行ERP客户端，每60秒自动刷新
- **问题**: 服务端每分钟承受3次全量数据查询（几千条数据），CPU持续高负载
- **解决**: 通过询问机制和窗口焦点检测，将无效请求减少90%以上

---

## 🔐 双重省流锁机制

### 第一道锁：专注模式锁（窗口焦点检测）

**原理**: 只有当ERP窗口处于激活状态时，才允许发起网络请求。

**效果**:
- ✅ 窗口最小化或切换到其他程序时，自动停止所有刷新请求
- ✅ 重新激活窗口时，立即触发一次检查，确保数据最新
- ✅ 多开场景下，只有当前使用的窗口消耗资源

**示例场景**:
```
用户A: 正在查看库存（窗口激活） → 每60秒询问一次
用户B: 切换到Excel工作（窗口失焦） → 完全静默，0请求
用户C: 下班忘记关机（窗口失焦） → 完全静默，0请求
```

### 第二道锁：时间戳比对锁（询问机制）

**原理**: 客户端每次刷新前，先发送一个极小的请求询问服务端"数据变了吗？"

**通信流程**:
```
客户端 → 服务端: GET /api/server/status (几字节)
服务端 → 客户端: {"last_change": 1701320000.123, "change_count": 42}

客户端判断:
- 如果 server_timestamp > local_timestamp:
    → 执行完整刷新（调用 load_inventory）
- 否则:
    → 跳过刷新，界面保持不变
```

**效果**:
- ✅ 数据无变化时：只传输约100字节（JSON时间戳）
- ✅ 数据有变化时：传输完整数据（几千条记录）
- ✅ 在"读多写少"的ERP场景下，90%的刷新都是无效的

**状态查询接口** (`api/routes/status.py`)
```python
# GET /api/server/status
# 返回: {"last_change": float, "change_count": int, "timestamp_readable": str}
```

### 客户端配置

**刷新频率设置** (`erp_settings.json`)
```json
{
  "client": {
    "refresh_interval": 60000  // 单位：毫秒，60000 = 60秒
  }
}
```

设置为 `0` 可禁用自动刷新。

## 🎓 技术细节

### 时间戳管理

```python
# 服务端维护全局时间戳
class DataChangeTracker:
    def __init__(self):
        self._last_change_time = time.time()
        self._change_count = 0
    
    def mark_data_changed(self, operation: str):
        self._last_change_time = time.time()
        self._change_count += 1
```

### 客户端询问逻辑

```python
def check_and_refresh(self):
    # 第一道锁：窗口焦点检测
    if not self.window_has_focus:
        return  # 窗口未激活，直接跳过
    
    # 第二道锁：时间戳比对
    status = self.api_client.get_server_status()
    if status['last_change'] > self.last_server_timestamp:
        self.load_inventory()  # 有变化，执行完整刷新
    else:
        pass  # 无变化，什么都不做
```

## ⚠️ 注意事项

1. **首次加载**: 客户端首次启动时，`last_server_timestamp=0`，会强制刷新一次数据

2. **网络异常**: 询问失败时静默忽略，避免频繁弹窗报错

3. **时间同步**: 使用浮点数时间戳（秒），精度足够，无需担心时钟偏差

4. **线程安全**: 时间戳管理器使用`threading.Lock`保护，支持多线程
